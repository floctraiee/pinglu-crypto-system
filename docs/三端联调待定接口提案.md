## 接口 1 · 设备公钥分发（100 台规模）

**问题**
方案第 20 段要求公钥「登记到边缘网关**和**中心平台」。现在中心**没有 `POST /devices`**（`/openapi.json` 已确认），只能直接改库；100 台无法手工。而且网关的预登记表和中心的 `devices` 表必须逐字节一致，否则验签结论不成立。

**建议**

- **唯一事实源**：`test_data/registry_public.json`，**只由 A 生成**，其他两人只导入、不修改
- 中心新增批量登记接口 `POST /devices`；网关继续用文件（`REGISTRY_PATH`）
- 两边都记录 SM3 公钥指纹，导入后各打印一份，三人核对

**字段**

```jsonc
// POST /devices
{
  "devices": [
    { "device_id": "WL-001", "device_type": "water_level",
      "public_key": "<128位hex>", "fingerprint": "<SM3(公钥字节) 64位hex>" }
  ]
}
// 200
{ "registered": 100, "updated": 0, "total": 100 }
```

**验收**：`GET /devices` 返回 100 台；三份指纹清单逐条一致。

## 接口 2 · 在线设备数（系统总览）

**问题**
方案要「在线设备数」，但中心不知道谁在线——在线状态只有 MQTT broker / 网关知道。

**建议（按代价从低到高）**

1. **最省事（推荐先用这个）**：不引入心跳，页面显示「**已注册设备数 / 已收到数据的设备数**」，由 `/devices` + `/stats` 算出来。方案原文并没有要求实时心跳。
2. 要真「在线」的话：网关定时 `POST /gateway/status`（见接口 4），中心用 `last_report_at` 判断；「在线」定义为最近 **30 秒**内有批次到达。

**字段（若走方案 2）**

```jsonc
// GET /stats 增加
{
  "devices_total": 100,
  "devices_seen": 87,          // 有数据到达过的设备数
  "devices_online": 85,        // 最近 30 秒内有数据
  "online_window_seconds": 30
}
```

**验收**：停掉若干设备后，页面上的数字在 30 秒内下降。

## 接口 3 · 异常类型分类（异常审计）

**问题**
方案第六节要「**异常类型**」，但中心的 `audits` 表只有 `status`（accepted/rejected/duplicate）+ `reason_code`（`INVALID_RECORD_HASH` 等）。方案第五节列的 7 类异常和 `reason_code` **不是一一对应**（比如「记录删除」和「伪造插入」都会得到 `INVALID_BATCH_RANGE`）。

**建议：不要让中心去猜，用「标签 + 判定」两列**

- **真值**（异常类型）：来自注入脚本的 `label.json`，写测试时自己知道
- **判定**（中心怎么说的）：`reason_code` + `affected_sequences`
- 测试脚本把两者对照，统计检测率/定位准确率/误报率
- 页面同时显示两列，更清楚也更可信

**`reason_code` ↔ 方案异常类型的对照表**

| 方案第五节异常类型 | 典型 `reason_code` | 检出方 |
|---|---|---|
| 1 内容修改 | `INVALID_RECORD_HASH` / `INVALID_MERKLE_ROOT` | 中心 |
| 2 记录删除 | `INVALID_BATCH_RANGE` | 中心 |
| 3 伪造插入 | `INVALID_BATCH_RANGE` / `INVALID_SEQUENCE` | 中心 |
| 4 时序乱序 | `INVALID_SEQUENCE` / `INVALID_HASH_CHAIN` | 中心 |
| 5 设备伪造 | `UNKNOWN_DEVICE` / `INVALID_SIGNATURE` / `INVALID_DEVICE_IDENTITY` | 网关 + 中心 |
| 6 历史重放 | `DUPLICATE_BATCH` / `BATCH_CONTENT_CONFLICT` / `INVALID_BATCH_SEQUENCE` | 中心 |
| 7 离线缓存篡改 | `BATCH_CONTENT_CONFLICT` | 中心 |
| （传输篡改） | 网关 `edge_result.reason_code` | 网关初验 |

**⚠️ 顺序陷阱（必须写进测试脚本注释）**
中心的**去重在验证之前**。同 `batch_id` 改内容 → 得到的是 `BATCH_CONTENT_CONFLICT`，**不会**走到逐条摘要定位。所以 1–5 类异常样本**必须用新的 `batch_id`**，否则拿不到 `affected_sequences`。第 6 类（重放）才故意沿用旧 `batch_id`。

**字段（`audits` 表增加）**

```jsonc
{
  "device_id": "WL-001", "batch_id": "WL-001-000013",
  "status": "rejected", "reason_code": "INVALID_RECORD_HASH",
  "affected_sequences": [3],
  "edge_verdict": "pending",              // 网关初判：pending/audit_pending
  "anomaly_type": "content_tampering",    // 仅当由注入脚本带标签时填写，可空
  "created_at": "2026-10-09T15:00:00+08:00"
}
```

## 接口 4 · 断网恢复的数据源 ★ 完全空白，优先级最高

**问题**
方案第六节要「网络状态、**缓存批次数**、**补传进度**、**断点位置**、恢复验证结果」。这些数据**全在网关的 SQLite**（`pending_batches` / `device_chain`），中心一无所知，页面（在电脑3）也够不着网关（在电脑2）。

**三个方案**

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A | 网关开只读 `GET /status`，页面直接 fetch | 实现最快 | 跨机要开端口；页面依赖两个后端 |
| **B（推荐）** | 网关定时 `POST /gateway/status`，中心存表，页面只连中心 | 单一数据来源；断网期间的数据恢复后补报；中心能用 `last_report_at` 判断网关是否活着 | 需要新表 + 新接口 |
| C | 页面只从批次到达间隔推断断档 | 不改任何后端 | 拿不到「缓存批次数 / 断点位置」，方案要求满足不了 |

**建议走 B。**「网络状态」= 中心看 `last_report_at` 距今多少秒；「补传进度」= pending 数量随时间下降；「断点位置」= `oldest_pending`；「缺失区间」见接口 5。

**字段**

```jsonc
// POST /gateway/status   （网关每 RETRY_INTERVAL 上报一次）
{
  "gateway_id": "edge-gateway-01",
  "reported_at": "2026-10-09T15:00:00+08:00",
  "mqtt_connected": true,
  "center_reachable": false,
  "cache": {
    "pending": 12, "audit_pending": 1,
    "accepted": 340, "rejected": 2, "duplicate": 8, "conflict": 0
  },
  "oldest_pending": {
    "device_id": "WL-001", "batch_id": "WL-001-000013", "first_seq": 121
  },
  "device_chain": [
    { "device_id": "WL-001", "last_sequence": 120, "last_batch_no": 12 }
  ],
  "attempts_total": 5
}
// 200
{ "status": "ok" }

// GET /gateway/status  （页面读）
{
  "gateway_id": "edge-gateway-01",
  "reported_at": "2026-10-09T15:00:00+08:00",
  "seconds_since_report": 4,
  "online": true,
  "cache": { "...": "同上" },
  "pending_trend": [ {"at": "...", "pending": 12}, {"at": "...", "pending": 7} ]
}
```

**验收**：停中心 → 网关 pending 增长、页面显示「网关在线 / 中心不可达 / 缓存 N 批 / 断点 seq X」；恢复中心 → 趋势图上 pending 归零。

## 接口 5 · 缺失区间识别

**问题**
方案第七节 5 与 10/12–13 任务要求「检查**缺失区间**」。中心现在遇到序号缺口只回一个 `INVALID_SEQUENCE`，**不说缺哪几段**。

**建议**
中心在批次校验时算出「期望序号」与「实际序号」的差集，放进 rejected 返回和审计记录。网关本地也能算（它知道自己的链尾），两边都显示。

**字段**

```jsonc
// POST /batches 的 rejected 返回里增加
{
  "status": "rejected",
  "reason_code": "INVALID_SEQUENCE",
  "device_id": "WL-001", "batch_id": "WL-001-000013",
  "expected_sequence": 121,
  "received_sequence": 131,
  "missing_ranges": [[121, 130]],     // 闭区间列表；无缺口时为空
  "affected_sequences": [131, 132, "..."]
}
```

**`audits` 表增加一列** `missing_ranges`（JSON 文本）。

**验收**：故意跳发一批（比如只发第 12 批），中心返回里能报出缺失的序号区间，页面「断网恢复」显示该区间。
