### 接口 4 · 断网恢复的数据源 ★

| 项 | 内容 |
|---|---|
| **提案建议** | **方案 B（推荐）**：网关定时 `POST /gateway/status`，中心存表，页面只连中心；「网络状态」用 `last_report_at` 距今秒数 |
| **实际实现** | **方案 A 的变体（文件版）**：网关每 `STATUS_INTERVAL`（默认 5 秒）把状态**原子写入** `edge_gateway/data/gateway_status.json`；中心 `telemetry._read_gateway_status()` 读该文件（候选路径含 `PINGLU_GATEWAY_STATUS` 环境变量） |
| **是否满足目的** | ✅ **满足**。页面能拿到：缓存批次数、缓存记录数、已补传、待补传、**断点序号 `break_sequence`**、最后接收/确认时间；中心侧自动汇总 `progress_percent` / `devices_with_backlog` |
| **差异** | 提案是 **HTTP 上报 + 中心存表**；实际是 **文件 + 中心读文件**。**取舍理由**：文件方案不需要新表、新接口、新事务，改动量约为方案 B 的 1/5；单机部署时"网关→中心"只是同盘拷贝，跨机部署时把文件同步或 `PINGLU_GATEWAY_STATUS` 指过去即可 |
| **审定结论** | **通过（方案变更，需在报告里说明）** |
| **落地位置** | `edge_gateway/status.py`（写出）、`edge_gateway/forward.py`（`run_forever` 里按间隔调用）、`center_platform/telemetry.py`（读取） |
| **字段约定** | `docs/gateway_status_contract.md`（本文件已补齐；提案注释里引用了它但之前不存在） |
| **⚠️ 部署注意** | 中心读的是**它自己仓库根**下的 `edge_gateway/data/gateway_status.json`。跨机部署时需把 B 的状态文件同步过去，或用 `PINGLU_GATEWAY_STATUS` 指向它 |

### 接口 5 · 缺失区间识别

| 项 | 内容 |
|---|---|
| **提案建议** | `POST /batches` 的 rejected 返回里加 `missing_ranges`；`audits` 表加同名列 |
| **实际实现** | ❌ **未实现**。全代码库搜 `missing_ranges` 无结果 |
| **现有替代** | `verify_batch` 返回 `affected_sequences`（哪些序号有问题）+ 错误文本「序号与接收端可信下一序号不一致」；**能定位"哪几条坏了"，但不能直接给出"缺了哪几段"** |
| **影响评估** | **不影响核心结论**。缺失区间属于「展示友好度」而非「判定正确性」：中心仍能正确判 `INVALID_SEQUENCE` 并拒绝；网关侧 `check_order.py` **能算出序号断层（实测 0 处）** |
| **审定结论** | **不实现，登记为已知限制**。报告里写「缺批检测由 `tools/check_order.py` 在网关侧完成，中心侧以 `INVALID_SEQUENCE` + `affected_sequences` 定位异常序号」 |
| **备注** | 若时间允许，`check_order.py` 的断层检测逻辑**可平移进中心**（约 1 小时），但目前优先级低于截图与报告 |
