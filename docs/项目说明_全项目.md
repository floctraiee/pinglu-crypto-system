# 平陆运河多源感知数据国密可信采集与篡改溯源系统

多源感知设备 → 边缘网关 → 中心平台的可信采集链路。设备端用 SM3 摘要链 + Merkle 树组织记录，
用 SM2 对批次签名；中心平台**不采信网关的通过状态**，用预登记公钥独立重验，
并对外提供单条记录的 Merkle 证明与签名复核。

当前实测（2026-10-17，口径见 `P33_实时延迟口径与数据_20261017.md`）：

| 项 | 结果 |
|---|---|
| 中心侧直连压测（100 台 / 18000 批 / 180000 条，中心 `DELETE + FULL`） | 全部 accepted，0 拒绝、0 审计，P95 **78.07 ms** |
| 三端联调轮（MQTT → 网关 → 中心） | 接收 5865 批 = 入库 5782 + 判拒 83（发送端跳批） |
| 三端实时延迟（无积压窗口 312 批） | P95 **740 ms**，99.36% ≤ 1 s；过载窗口 P95 174.6 s（排队主导） |
| 三端持续吞吐 | 约 90 条/秒，**未达** 100 条/秒（发送端批次组织与网关转发节拍受限） |
| 检测能力（14 个带标签用例） | 严格 9/9、宽松 11/11，定位 5/5，误报 0/3（样本为项目自建） |
| 签名 / 验签（每批 1/10/20 条） | 5.17/5.19/5.23 ms、8.34/8.38/8.42 ms，报文 832/4489/8559 B |

## 1. 环境与安装

| 项 | 版本 |
|---|---|
| Python | 3.14（三人统一） |
| 操作系统 | Windows（命令按 CMD 写，PowerShell 见 §4） |
| MQTT Broker | Mosquitto 2.x（仅 MQTT 链路需要） |

```bat
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

依赖已锁版本：`gmssl==3.2.2`、`fastapi==0.143.0`、`httpx==0.28.1`、`uvicorn==0.54.0`、
`pytest==9.1.1`、`paho-mqtt==2.1.0`。下文命令里的 `python` 均可替换为
`.venv\Scripts\python.exe`。

**首次运行或要清到干净起点时**，先在仓库根目录执行一次初始化：

```bat
python init_project.py
```

它会生成/校验七类设备密钥（`keys/`，不入库）、写出公开登记表（`test_data/registry_public.json`）、
按登记表重建中心 `devices` 表、清空 `batches`/`records` 并把模拟器链尾状态复位；
`--dry-run` 只打印不改动，`--reset-audits` 连审计一起清空，改动前自动备份到
`center_platform/data/init-backup/`（该目录不入库）。

## 2. 单机四终端跑通（最快路径）

按顺序开四个 CMD 终端，都在仓库根目录：

```bat
:: 终端 1 — MQTT Broker
mosquitto -c mosquitto.conf -v

:: 终端 2 — 中心平台
python -m uvicorn center_platform.main:app --host 127.0.0.1 --port 8000

:: 终端 3 — 边缘网关
python -m edge_gateway.main

:: 终端 4 — 设备模拟器（七类各一台，每台每秒 1 条，每批 10 条，发一轮）
python -m device_simulator.runner --devices 7 --rate 1 --batch-size 10 --rounds 1 ^
  --keys-dir keys --registry test_data/registry_public.json --db-path simulator.db ^
  --broker 127.0.0.1 --port 1883
```

| 地址 | 用途 |
|---|---|
| http://127.0.0.1:8000/ | 中心页面（六块：总览 / 七类感知数据 / 异常审计 / 批次细节与 Merkle 证明 / 离线恢复 / 性能对比） |
| http://127.0.0.1:8000/docs | Swagger，可直接提交一批 JSON 手工验证 |

期望：终端 3 打印 `[接收] <设备> <批次> seq a~b 初验通过` 与 `[转发] ...`，
页面总览的批次/记录数增加，点开某条记录能看到叶摘要、路径与验签结果。

## 4. 配置项

所有地址、端口、库路径都可用**同名环境变量**覆盖，业务代码不写死。完整样例见
[`.env.example`](.env.example)（仓库不自动加载它，需要按下面的方式设置）。

**中心平台**

| 变量 | 默认值 | 说明 |
|---|---|---|
| `PINGLU_CENTER_DB` | `center_platform/data/center.db` | 中心库路径；异机/实测时切换 |
| `PINGLU_SIMULATOR_DB` | `simulator.db` | 离线页降级读取的待发队列路径 |
| `PINGLU_GATEWAY_STATUS` | 见 §7 | 网关只读状态文件路径，优先级最高 |
| `PINGLU_SQLITE_JOURNAL` | `WAL` | 中心库 journal 模式；设 `DELETE` 可回退到优化前配置做对照 |
| `PINGLU_SQLITE_SYNC` | `NORMAL` | 中心库 synchronous；设 `FULL` 可回退做对照 |

> SQLite 持久化说明：中心默认 `WAL + synchronous=NORMAL`（进程崩溃不丢已提交事务，
> 突然断电可能丢最后若干事务）；网关缓存库固定 `WAL + synchronous=FULL`，不做可配。
> 报告里 18000 批 / 180000 条的中心侧压测（P95 78.07 ms）是在优化前 `DELETE + FULL` 下测的，
> 2 分钟对照（1200 批）才用 WAL + NORMAL，详见 `验证结果_优化前_2分钟.csv`、
> `验证结果_优化后_2分钟.csv`。

**边缘网关**

| 变量 | 默认值 | 说明 |
|---|---|---|
| `MQTT_BROKER` / `MQTT_PORT` | `127.0.0.1` / `1883` | Broker 地址与端口 |
| `MQTT_TOPIC` | `pinglu/batches/+` | 订阅主题 |
| `CENTER_URL` | `http://127.0.0.1:8000` | 中心地址 |
| `DB_PATH` | `edge_gateway/data/edge_cache.db` | 网关缓存库 |
| `REGISTRY_PATH` | `test_data/registry_public.json` | 预登记公钥（**只能用主登记表**） |
| `RETRY_INTERVAL` / `HTTP_TIMEOUT` | `5` / `10` | 重试节拍、单次 POST 超时（秒） |
| `MAX_MESSAGE_BYTES` | `1048576` | 单条 MQTT 消息上限 |
| `MAX_PER_DEVICE_PER_ROUND` | `20` | 一轮转发里同一设备最多连发几批（串行按序） |

查看网关当前生效配置：

```bat
python -m edge_gateway.config
```

设置方式（两者等价，任选其一）：

```bat
:: CMD
set CENTER_URL=http://192.168.1.30:8000 && python -m edge_gateway.main
```

```powershell
# PowerShell
$env:CENTER_URL = "http://192.168.1.30:8000"; python -m edge_gateway.main
```

网关也支持命令行覆盖：`--broker / --port / --topic / --center / --db / --interval`。

## 6. 设备端

七类设备：水位 `WL`、气象 `WE`、航标 `NM`、边坡 `SL`、船闸 `LK`、无人机 `DR`、测量船 `SB`。
100 台测试表示扩展模拟设备数量，不是增加设备类型。

### 6.1 固定样例与本地检查

以 WL-001 身份重新签名并验证过的样例随仓库提供：

- 正常批次：`test_data/verified_wl001/normal_batch.json`
- 配套公开登记表：`test_data/verified_wl001/registry_public.json`

```bat
python -m device_simulator.publish --batch-file .\test_data\verified_wl001\normal_batch.json ^
  --registry .\test_data\verified_wl001\registry_public.json --dry-run
```

预期显示本地验签与合同检查通过，批次为 WL-001-000001，主题 `pinglu/batches/WL-001`。
`--dry-run` 不连接 Broker、不发消息，显示“未连接 Broker”属正常。

### 6.2 发布到 Broker

```bat
python -m device_simulator.publish --batch-file .\test_data\verified_wl001\normal_batch.json ^
  --registry .\test_data\verified_wl001\registry_public.json --broker <网关IP> --port 1883 --timeout 15
```

MQTT PUBACK 只表示 Broker 已接收；中心是否入库、网关是否完成任务要另行核对。
当前联调应显式指定 `--batch-file` 与 `--registry`，不使用默认 `--sample`。

### 6.3 多设备、控速率、控批量

```bat
python -m device_simulator.runner --devices 7 --rate 1 --batch-size 10 --rounds 1 ^
  --seed 2026 --keys-dir keys --registry test_data/registry_public.json --db-path simulator.db
```

| 参数 | 含义 |
|---|---|
| `--devices` | 设备数，按七类循环分 ID |
| `--rate` | 每台设备每秒生成记录数 |
| `--batch-size` | 每台设备每批记录数 |
| `--rounds` | 生成轮数；每轮每台一批 |
| `--seed` | payload 随机种子（可复现） |
| `--keys-dir` / `--registry` / `--db-path` | 私钥目录、公开登记表、模拟器状态库（均必填） |
| `--broker` / `--port` | 提供后才尝试发送已落盘的待发批次；断网期间只生成、不断链 |

> **上面这条命令会改写仓库里的两个文件。** `--registry test_data/registry_public.json`
> 会被 `register_devices()` 重写，`--db-path simulator.db` 会写入模拟器状态。
> 更关键的是：`keys/WL-001.json` 的公钥与 `test_data/registry_public.json` 里的 WL-001 公钥
> **不是同一把**（其余 6 台一致）。在仓库根目录跑完本命令后，§6.1 的
> `verified_wl001/normal_batch.json` 会以 `INVALID_SIGNATURE` 验签失败。
> 只想验证「能独立生成数据」时，请用 §6.4 的隔离路径。

### 6.4 独立生成设备数据（不连 Broker，21 批 / 210 条）

不需要 Broker、不需要中心平台，也不改动 `keys/`、`test_data/registry_public.json` 与根目录的
`simulator.db`：所有产物都落在 `_tmp/gen21/`（该目录已在 `.gitignore` 中）。

```powershell
python -m device_simulator.runner --devices 7 --rate 1 --batch-size 10 --rounds 3 --seed 2026 --keys-dir .\_tmp\gen21\keys --registry .\_tmp\gen21\registry_public.json --db-path .\_tmp\gen21\simulator.db
```

预期输出 21 行「已生成并保存 …」，7 台设备（WL/WE/NM/SL/LK/DR/SB-001）各 3 批，
批次号到 `*-000003`、序号到 `21~30`，合计 **21 批 / 210 条记录**。
核对：`_tmp/gen21/simulator.db` 的 `generated_batches` 应为 21 行。

`--rounds` 决定批次数：`--rounds 1` 只有 **7 批 / 70 条**，要 21 批 / 210 条必须用 `--rounds 3`。

### 6.5 已验证结果

- 全套 pytest：32 passed、14 subtests passed（3 条弃用警告）。
- 单设备重启续链：4 批、40 条记录检查通过。
- 独立生成（§6.4，`--rounds 3`，隔离路径）：21 批、210 条记录，7 台设备各 3 批（未发 MQTT）。
- 100 台三轮本地测试：300 批、3000 条，批次校验、逐条摘要与跨批次摘要链全部通过（未发 MQTT）。
- 已完成一次真实三端联调（结果见文首与 `P33_实时延迟口径与数据_20261017.md`）。

100 台三轮本地测试未发送 MQTT，不能代表“100 台运行 30 分钟”的三端结论；
三端口径请以 §10 的证据文件为准。

更细的设备端记录见 `docs/a_crypto_simulation_notes.md`。

## 7. 边缘网关

```bat
python -m edge_gateway.main
```

启动后依次打印生效配置、预登记设备清单、从数据库恢复的未确认批次数与队列状态。
网关只用 `REGISTRY_PATH` 的预登记公钥验签，**不使用消息里自带的公钥**；
初验失败的批次不丢弃，原文与初判一并落库并送中心复核。

- 缓存库默认 `edge_gateway/data/edge_cache.db`，对 `device_id + batch_id` 唯一约束；
- 转发按设备与批次号升序推进，前一批未获中心终态时后续不抢跑；
- 只有中心明确返回 accepted / 已记审计的 rejected / 内容一致的 duplicate 才标记已确认；
- 传输失败、超时、5xx 一律保留待传，重启从数据库恢复队列。

**离线页数据来源**：中心 `/offline-status` 优先读网关只读状态文件
`edge_gateway/data/gateway_status.json`（可用 `PINGLU_GATEWAY_STATUS` 指向别处），
文件不存在时自动降级读 `PINGLU_SIMULATOR_DB`（`simulator.db`）的待发队列。
状态文件字段样例见 `test_data/gateway_status_sample.json`：

```json
{
  "generated_at": "2026-10-14T17:20:00+08:00",
  "devices": [
    {
      "device_id": "SL-001",
      "device_type": "slope",
      "cached_batches": 3,
      "cached_records": 30,
      "resend_done": 2,
      "resend_pending": 3,
      "break_sequence": 21,
      "last_gateway_received_at": "2026-10-14T17:12:05+08:00",
      "last_center_ack_at": "2026-10-14T17:12:09+08:00"
    }
  ]
}
```

注意：该状态文件目前**尚未由网关写出**，离线页显示的是降级来源，页面上会标注实际数据源。

## 8. 中心平台

```bat
:: 单机
python -m uvicorn center_platform.main:app --host 127.0.0.1 --port 8000
:: 三机（被另两台访问）
python -m uvicorn center_platform.main:app --host 0.0.0.0 --port 8000
```

| 接口 | 方法 | 用途 |
|---|---|---|
| `/health` | GET | 健康检查 |
| `/batches` | POST | 接收批次，返回 accepted / rejected / duplicate |
| `/devices`、`/batches`、`/records`、`/audits`、`/stats` | GET | 登记表、批次、记录、审计、统计 |
| `/batches/{batch_id}/proof/{sequence}` | GET | 单条 Merkle 证明（叶摘要、路径、根、复验结果） |
| `/batch-raw` | GET | 按设备 + 批次回读原始批次 |
| `/verify-signature` | POST | 用中心预登记公钥复核签名 |
| `/offline-status` | GET | 缓存数、断点、补传进度、实时延迟 |
| `/performance` | GET | 签名对照数据与来源文件信息 |

登记表导入（中心没有 `POST /devices`，必须用脚本）：

```bat
python tools\import_registry.py --dry-run        :: 只看会导入什么
python tools\import_registry.py                 :: 写库
python register_all_devices.py                  :: 同类工具（原样登记公开登记表）
```

导入前后务必确认 `PINGLU_CENTER_DB` 与中心服务使用的是同一个库。

## 9. 测试与实验

```bat
:: 单元与集成（合并前必须全绿）
python -m pytest -q

:: 中心功能冒烟（自带临时库，不写正式库）
python 验证脚本_中心功能冒烟.py

:: 页面六块接口实测（先起中心）
python 验证脚本_页面接口.py http://127.0.0.1:8000

:: 造一份七类设备 + 多种异常的页面演示库
python 验证脚本_搭建页面数据.py center_platform/data/demo.db
```

| 目的 | 命令 | 输出 |
|---|---|---|
| 检测率 / 定位准确率 / 误报率 | `python tests/evaluate.py --make-samples --out test_data/eval_samples.json`，再 `python tests/evaluate.py --samples test_data/eval_samples.json --submit --url http://127.0.0.1:8000` | 汇总 JSON + 明细 CSV |
| 签名批次对照 | `python tests/benchmark_signing.py --records 100` | `docs/evidence/benchmark_signing_<日期>.csv` |
| 100 台规模压力 | 先 `python 验证脚本_建百台环境.py --devices 100`，把中心以 `PINGLU_CENTER_DB` 指向 `_tmp/stress100/` 的库，再 `python tests/stress_center.py --devices 100 --minutes 30 --batch-size 10 --url <临时中心地址> --registry <临时登记表> --keys-dir <临时密钥目录>` | 汇总 CSV/JSON |
| 百台临时环境 | `python 验证脚本_建百台环境.py --devices 100` | `_tmp/stress100/`（临时登记表、密钥、干净中心库） |
| 网关 → 中心打通 | `python 验证脚本_端到端打通.py --center http://127.0.0.1:8000 --device WL-001` | 转发结果与延迟统计 |
| 单批逐项核验 | `python tools/verify_batch.py --batch test_data/normal_batch.json` | 分项 PASS/FAIL，退出码 0/1 |
| 闭环与拒绝演示 | `python demo_closed_loop.py`、`python demo_rejections.py` | 控制台逐步输出 |
| 恢复正式库 | `python 验证脚本_一键恢复.py --dry-run`（确认后再去掉 `--dry-run`） | 备份 + 恢复记录 |

测试脚本的库隔离方式不同，用之前先看清：

- **中心功能冒烟 / 页面接口 / 端到端打通**自带临时库或只读，脚本会自检路径，
  发现指向正式库直接拒绝运行；
- **规模压力（`tests/stress_center.py`）**按 `--url` 往它指向的中心写数据，
  所以必须先把中心起在临时库上（`PINGLU_CENTER_DB=_tmp/...`），
  并用 `--registry` / `--keys-dir` 指向 `_tmp/stress100/` 下的临时登记表与密钥；
- **`init_project.py`、`验证脚本_一键恢复.py`**会改动正式库，跑之前先用 `--dry-run` 看会改什么。

## 11. 常见问题排查

| 现象 | 先查什么 |
|---|---|
| 设备发了但网关没收到 | Mosquitto 是否启动、`MQTT_BROKER`/`MQTT_PORT`、主题 `pinglu/batches/+`、防火墙 1883 |
| 网关连不上中心 | `CENTER_URL` 是否指向对的主机与端口、中心是否 `--host 0.0.0.0`、防火墙 8000 |
| 批次被判 `UNKNOWN_DEVICE` | 中心 `devices` 表是否已导入且与登记表一致（`tools/import_registry.py --fingerprint-only` 核对指纹） |
| 验签一直失败 | 登记表是否加载了**主登记表**（`test_data/registry_public.json`）；不要指向 `test_data/migration_wl900_to_wl001/`（合并冲突中间产物，公钥不匹配）；再逐字比对双方 canonical 输出 |
| 提交总是 `BATCH_CONTENT_CONFLICT` | 历史残留：同一 `batch_id` 内容不同。先 `python init_project.py` 复位链尾（会自动备份） |
| 断网后少数据 | 写入 SQLite 的事务是否提交、`pending` 是否只在中心确认后才改、重启后的队列扫描是否完整 |
| 中心收到两次 | QoS1 与 HTTP 超时都会重试，按 `device_id + batch_id` 幂等，不依赖“恰好一次” |
| 离线页数字对不上 | 网关状态文件未写出时页面降级读 `simulator.db`，页面会标注实际来源 |
| 三端吞吐上不去 | 发送端是否每批重连 MQTT、待发队列是否按 `device_id + batch_id` 串行、网关 `MAX_PER_DEVICE_PER_ROUND` 与转发轮询间隔 |
| 端口被占 | 用 `netstat -ano` 找到占用 8000（或 1883）的进程后结束它，或换端口启动 |

## 12. 仓库约定

- **不进 Git**：`keys/`（私钥）、`.venv/`、`*.db`、`*.docx`、`报告图_*/`、含个人路径的日志、`backup/`、`_tmp/`。
- **公开登记表**只含 `device_id / device_type / longitude / latitude / public_key`，不含私钥；
  导入中心后逐台核对公钥 SM3 指纹。
- **合并前**必须跑 `python -m pytest -q` 并记录结果；问题按「复现命令、期望、实际、日志」四段记录到 `docs/progress.md`。
- **验证脚本分两类**：冒烟/页面/打通类会自检库路径，指向正式库直接拒绝运行；
  压力与初始化类会真的写库，动手前先 `--dry-run` 或先把中心指向临时库（见 §9）。
- **报告数字必须可追溯**：任何写进报告的指标都要能在证据文件里查到，且口径写清
  （中心侧直连 / 三端实时 / 过载窗口）。
